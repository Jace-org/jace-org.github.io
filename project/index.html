Module project concept

Honeypot Lab

A web-based honeypot management and security assessment portal. Attackers hit deliberately weak decoy services, analysts manage the response in a portal, and then the portal itself is attacked, fixed and retested.

The idea

Most security projects either break things or defend things. This one does both in one story. A honeypot lures and records attackers. A management portal, used by a small security team, turns those records into cases, blocklists and alerts. The portal is then treated as a real application under assessment: its vulnerabilities are found, demonstrated, fixed and proven fixed.

How it fits together

  1. Decoys are intentionally vulnerable web pages and a fake API. They never hold real data and have no outbound internet access.
  2. Event capture records every probe (who, what, when, which payload type) and classifies it, for example SQL injection, XSS or path traversal.
  3. The portal is where analysts log in to review events, open incidents, block sources and set alert rules.
  4. Assessment is the second half: the portal is attacked with standard tools, the flaws are fixed, and the same tests are run again.

Portal modules

Users & roles

Admin and analyst accounts, secure login, role-based access.

Incidents

Open, triage, assign and close cases built from captured attacks.

Blocklist

Maintain a watchlist of hostile sources with notes and expiry.

Alert rules

Choose what counts as serious and where the notification goes.

Security assessment plan

The portal is first built with a small set of realistic, documented weaknesses. Each one follows the same loop: find it, demonstrate it, fix it, retest it.

Weakness class What it shows Type of fix
Injection Unsafe handling of search input Safe query handling, input validation
Cross-site scripting Untrusted notes shown back to users Output encoding, content security policy
Broken access control Analysts reaching admin functions Server-side role checks
Insecure direct object reference Viewing another user's cases by changing an ID Ownership checks on every request
Weak session handling Predictable or long-lived sessions Hardened cookies, expiry, rotation

Technology

  • Backend: Flask REST API
  • Frontend: Jinja2 templates
  • Database: MySQL
  • Authentication: session or token based, with hashed passwords
  • Testing: Burp Suite, Nmap and manual checks
  • Version control: Git and GitHub

What gets delivered

  • A working portal with four management modules and two user roles
  • Honeypot decoys feeding real attack data into it
  • A threat model and an ethics and legal statement
  • A findings table: vulnerability, evidence, fix, retest result
  • A written report with before-and-after comparison

Try it

There is an interactive walkthrough of the whole idea: fire simulated attacks, work cases in a mock portal, and compare vulnerable and hardened builds. It runs entirely in your browser with made-up data.

Ethics and scope

All testing is carried out only on systems I own, inside an isolated, authorised lab environment. The decoys hold no real data, cannot reach the internet, and never execute anything an attacker uploads.
